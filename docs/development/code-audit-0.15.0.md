# 0.15.0 全项目审查

[返回开发指南](README.md) · 审查日期：2026-11-18 · 代码基线：`dev` 的 `08be2a3`。以下位置和结论对应此提交。

最先要修三件事：跨盘恢复会先删目标再报错；B 已收到停止仍可能执行下一步；更换 B 后旧方案可能写到新机器。这三项都用隔离数据验证过。P1 表示可能丢失实例现有文件、违背停止请求或写错目标；P2 表示任务卡住、功能失败或服务受阻；P3 表示发行可复现性问题。

## P1：优先修复

### R01　跨盘恢复失败前已删除目标

位置：`mcai/operation_context.py:979`、`:994–1002`。恢复候选建在 B 数据目录，校验通过后先 `unlink` 或 `rmtree` 实例中的目标，再用 `os.replace` 移入候选。Windows 不支持用这个调用跨卷移动。

**实测：** B 数据在 E 盘，实例在 C 盘。先备份并修改一个标记文件，再调用真实 `apply_plan` 恢复。结果是 `WinError 17`、实例中的目标不存在、原始备份仍在。目录经过相同的先删后换路径，本轮没有对真实存档做删除实验。**验收：** 文件和目录均在目标卷准备候选；切换失败时旧目标仍可用；分别验证同盘、跨盘和替换失败。

### R02　停止已经落盘，后续修复仍执行

位置：`mcai/host.py:523–530`、`mcai/operation_context.py:54–57`、`:803–815`。取消接口既写独立的 `cancel` 记录，也修改 `operation`。辅助进程用之前读出的整条 `operation` 保存进度，可能把后写入的取消标志覆盖；步骤之间只检查这条可被覆盖的记录。

**受控复现：** 安排「备份、写文件」两步，在备份查询终端状态时插入取消接口相同的两次落盘，再让修复继续。独立记录为 `cancel_requested=True`，操作记录中该字段消失，两步均执行，标记文件由 `before` 变成 `changed`。**验收：** 已持久化的取消请求不可被进度更新撤销；当前安全步骤可结束，下一步不得开始。按上述交错顺序检验，比依赖随机并发更可靠。

### R03　切换到另一台 B 后，原方案仍可写入同路径的实例

位置：`mcai/settings.py:143–177`、`mcai/astrbot_agent.py:190–222`、`mcai/operation_context.py:59–64`。任务等待批准时可以没有 worker，此时 A 允许替换 B 连接。后续批准走新连接；新 B 查不到操作号时，A 核对方案、规则和目录，未核对生成方案的 B 身份。两台 Windows 主机可有相同的实例名和绝对路径。

**受控复现：** 使用匹配的审核摘要和目录，让新 B 的操作查询返回 404。实际 `prepare_apply` 返回 `True`，随后用独立 B 数据目录调用真实执行路径，标记文件被原方案改写。未连接两台物理机，也未对生产实例写入。**验收：** 旧方案不能在另一台 B 上执行；同一 B 只换公网 IP 时仍能续接。核对的是 B 的持久身份，不能只比地址字符串。

## 另两项边界

- **R11 · P2 · Probe 并发扫描可能长时间轮不到。** `mods/mcai-probe/common/src/main/java/dev/mcai/probe/ProbeCore.java:27`、`:73–80`、`:347`、`:527–540`。最多接收四个扫描；每 tick 从插入顺序第一项开始，共享 1 ms。前项若每轮吃满预算，后项连取消检查也轮不到。此项来自控制流，未在本轮实服压测中复现。可用慢扫描加短扫描验证每项在有限 tick 内获得进度，且已取消的请求及时结算。
