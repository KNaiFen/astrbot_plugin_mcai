# 自动化审核专项评估（2026-11-15）

[开发索引](README.md) · [审核设计](../design/agent.md) · [状态与恢复](../design/storage-and-recovery.md)

## 结论与范围

当前自动审核已经形成真实的执行门槛：诊断脚本、诊断控制台命令、修改提案分别进入独立模型请求；原始参数与外部脚本正文会提交审核；明确拒绝、协议错误及已识别的材料缺失不会被当作允许；文件修复、一次管理员批准、多轮方案范围、原编号恢复也有专门实现。

但它目前更擅长审查“这段命令或方案表面上是否符合任务和规则”，还不能充分承担“独立核实主模型事实依据、发现主模型被错误线索误导”的职责。主要原因是首次审核没有诊断证据，部分执行效果没有体现在送审步骤里，管理员实际看到的批准材料又主要取决于模型摘要。

本轮确认 **9 项问题：2 项 P1、7 项 P2**。其中既有材料与知情批准缺口，也有已复现的执行顺序、陈旧诊断和恢复误拒绝。材料缺口不等于已测得真实审核模型错误放行；本轮没有使用实际计费模型评估误放行率或误拒绝率。

- 评估日期：2026-11-15；生产实现基线：本地 `dev` 的 `509e7adc38ef07175a7267479b920c0956508a36`。
- 范围：全部 39 个模型工具、A 端材料构造与审核协议、B 端主要执行路径、管理员批准、多轮续批、反馈并发、暂停与恢复、相关测试。
- 方法：四个模块独立检查后交叉核对；源码追踪、真实函数临时目录实验、真实 AstrBot v4.29.4 runner／HTTPS／隔离测试终端验证。
- 交付：评估与整改建议；不修改产品逻辑，不改变审批层级，不部署、不推送。
- 版本说明：当前开发态包含一次批准多轮方案，不能把本报告直接当作公开 0.11.1 发行包的逐字审查。
- 工作区说明：检查开始时工作区干净；期间另有并行任务修改部分测试及测试说明，生产实现没有发生差异。本轮既有测试结果按实际工作区描述，不宣称为干净提交快照的全套验证。

P1 表示应优先处理、会影响审核对生产动作或事实依据的判断；P2 表示明确的材料、流程或可用性缺陷。优先级与验证强度分开记录。

## 当前审核实际拿到了什么

首次审核的请求由 `mcai/agent_runtime.py:441-450` 组装：

| 字段 | 实际内容 |
|---|---|
| `task / instance / report` | 任务名、绑定实例 ID、创建时原文 |
| `feedback` | 插件保存的补充，包含外层身份字段 |
| `tool / arguments` | 原始工具名和实际调用参数，包含内联命令、脚本或步骤 |
| `script_declarations` | 主模型声明的外部脚本列表及编码 |
| `material` | B 读取的脚本正文、目录与工作目录、PowerShell 路径，以及按动作附加的启动 BAT、下载记录、备份清单和区块导出清单 |

续批额外获得已批准快照、最近四条工具消息的正文、上一批修复记录，见 `mcai/agent_runtime.py:451-460`。审核请求没有执行工具（`:494-499`），不能自行补读日志、配置、脚本依赖或备份正文。

### AR01：审核没有足够材料独立核实主模型的依据

**位置：**`mcai/agent_runtime.py:441-460、494-499`。

首次审核完全没有主模型此前的工具结果，也没有可以追溯到实际工具记录的证据引用。例如：

- 整份覆盖配置时，审核能看到新内容，但没有原配置，无法独立核对是否保留了无关配置和用户已有修改。
- 卸载或替换组件时，审核可能看到下载来源、版本和依赖，却没有当前组件清单、实际 MC／加载器版本和故障现场。
- 按日志、玩家陈述或网页提出修复时，审核能看到任务原文和补充，却看不到主模型核实这些线索时实际读到了什么。
- 目标绑定理由、候选实例描述和排除其他目标的实际结果，也没有随首次审核传入。

**验证：**给任务主对话放入独立的工具证据标记和模型解释标记，用真实 `Reviewer.decide` 构造请求，两个标记都没有进入审核 prompt。审核输入只有上表所列八个字段。该实验使用受控回复，没有让真实模型判断样例。

续批的最近四条工具消息也不能解决此问题：只提取 `message['content']`，没有配套工具名、参数和记录 ID；关键查询可能早于最近四条，或者已经被主对话压缩。较早证据不存在于本次审核材料，不代表它已被否定或已经不重要。

**影响：**独立审核容易重复依赖主模型已选定的范围和解释。它能检查显眼的不当命令，却缺少纠正“主模型把现象当原因、选错对象、误读证据”的必要事实。不能以“审核模型独立请求”推导“事实判断独立”。

**最小整改：**复用持久化的实际工具调用与结果，为本次动作提供有关的工具名、参数、结果及来源记录，至少覆盖目标、实际范围和修改前关键状态。主模型可以选择证据引用，但程序应从真实记录取材料；不要恢复一个由主模型自由陈述、无法追溯的申报段落来代替证据。超限时明确缩小范围或补查询，不静默裁剪。

**验收：**构造“模型摘要与实际查询结果矛盾”的良性样例，确认审核请求保留实际证据；续批和历史压缩后仍能定位关键结果。真实模型能否据此纠错，需要另做语义评估。

### AR02：送审步骤与执行器实际启停不一致

**位置：**`mcai/astrbot_agent.py:440-479`；`mcai/operation_context.py:564-588、702-705、813-815、922-923、1019-1027`。

送审的是原始 `steps`。执行器先按整组步骤判断是否需要快照，然后可能在任何步骤之前停服、在在线命令之前启动、在全部文件步骤之后自动启动。

**前提：**服务端原先运行；以下实验使用真实 `OperationContext.apply_plan`、临时 Store 和记录动作的替身控制台，没有启动真实 MC。

| 送审步骤 | 实际行为 | 结果 |
|---|---|---|
| 仅 `write_text config.txt` | 停服 → 写文件 → 启动 | 没有显式 `start` 仍自动启动 |
| 仅 `command whitelist add Tester`，附 `backup_paths: ['whitelist.json']` | 停服 → 启动 → 在线命令 | 给在线操作增加备份会引入一次停服启动 |
| `command say Maintenance starts now` → `write_text config.txt` | 停服 → 启动 → 公告 → 文件步骤拒绝 | 公告在重新启动后发送；文件没改，已产生额外启停 |

第三个场景明确返回 `修改文件前服务端必须停止`，文件仍为原内容。执行器已经为了在线命令自动启动，后面的文件步骤因此失败。

文件修复先停服属于既定约束。缺陷在于自动重新启动、在线备份导致的停服、实际启停时点和步骤失败无法从送审原文准确获知。运行时规则 `mcai/agent_rules.md:47` 还要求“需要重启时再显式 start”，与当前自动启动行为不一致。

**影响：**审核可能按“在线调整”理解本批，而实际发生停服；只允许在线动作的 continuation 也无法靠原始动作名完整表达实际范围。审核通过的步骤顺序不保证实际效果顺序。

**最小整改：**先对齐文件修复是否自动恢复运行、在线命令带备份是否允许隐式停服的产品语义，再让审核与批准材料表达有效动作及顺序。复用同一份有效执行描述，避免审核侧和执行侧各自推算。不要增加一次额外审批来掩盖语义不一致。

**验收：**覆盖以上三种场景，核对送审动作、批准展示和真实控制台调用；在线命令不能因无声的快照逻辑额外停服；混合步骤要么按已申报顺序完成，要么在产生效果前明确拒绝。

### AR03：二级脚本材料不完整

**位置：**`mcai/review.py:25-52`；`mcai/operation_context.py:249-265`；`mcai/astrbot_agent.py:498-501`。

材料函数只读取主模型列出的 `script_files`，字面量引用检查也只扫描顶层命令。已读取脚本的正文不会继续检查；自动加入的 `start.bat` 更是在顶层扫描之后才被追加。

**验证：**临时目录中，顶层明确调用 `outer.ps1`，该文件正文明确调用 `inner.ps1`，但只申报前者，返回的材料也只有前者，不报告后者缺失。另一个样例的 `start.bat` 只包含 `@call run.bat`，自动收集也只返回 `start.bat`。

执行前哈希清单从已经返回的 `material.scripts` 生成，因此漏掉的依赖也不在这份复核清单里。

**影响：**之前“完全不提供脚本正文”的问题已有修正，但目前的“正文齐全”只覆盖声明文件和顶层常见引用。审核员可能只能看到包装脚本，仍须自行发现缺项并拒绝；不能据此宣称所有实际执行脚本都已提供和绑定。本轮没有验证真实模型一定会放行材料不完整的调用。

**最小整改：**对明确、常见的字面量脚本依赖补齐正文或明确报告缺项，自动收集的启动脚本也采用相同规则；保留不实现通用 Shell 解析器的边界。动态路径及无法确定的效果继续要求澄清。

**验收：**普通二级脚本和启动 BAT 依赖，在材料不完整时明确拒绝；材料完整时，相关正文与执行前校验范围一致。

### AR04：实际配置和恢复内容仍有材料盲区

**有效启停配置：**`mcai/configuration.py:18-35` 的 `launcher_identity` 包括 Java、停服命令、超时和重启提示等配置。但 `mcai/operation_context.py:247-265` 只提供 PowerShell 路径、身份哈希和 BAT 正文，没有提供有效 `java_path / stop_command / stop_timeout / restart_prompt`。实际停服在 `mcai/console.py:247-248` 使用配置中的命令和超时。

真实材料函数实验确认返回字段仅为 `backups / chunk_exports / cwd / directory / downloads / launcher_identity / powershell_path / scripts`。哈希有助于证明配置没变，不能让审核理解抽象 `stop/restart` 最后使用什么命令和环境。

**恢复内容：**`mcai/operation_context.py:272-274` 只提供备份 manifest。该清单的 `files` 只记原先是否存在、是否为目录，见 `:716-753`；里面的 `plan` 是生成备份时准备实施的修改，不是备份保存的旧内容。真正恢复会删除当前目标、复制旧文件或目录，见 `:900-920`。

**影响：**审核知道恢复涉及哪些路径，却无法核对相关配置或脚本会恢复成什么。普通备份也没有与下载校验、区块导出相同的内容指纹绑定。这里确认的是材料与绑定能力缺口；没有复现正常产品流程自动改写既有备份，也不把外部手动修改备份假定为必然发生。

**最小整改：**提供本次动作真正使用的有效配置；恢复提供明确的备份身份、相关文件指纹及必要的文本差异／脚本正文。大世界数据用范围和结构化摘要，不把整份世界塞进上下文。相关内容需要绑定时，沿用现有执行前复核机制。

**验收：**审核可以直接读到有效停服命令和 Java 选择；恢复相关配置时能区分“旧内容”和“当时准备写入的新内容”。

### AR05：管理员的批准展示不保证包含关键动作

**位置：**`mcai/tasks.py:32-36、488-497`；`main.py:253-264`；`mcai/tool_schemas.py:867-890`；`mcai/agent_runtime.py:401-410、441-450`。

提案通知及 `/mcaiplan` 都主要展示模型的 `summary`，加可选 continuation 和在线命令无备份提示，没有确定性展示 `steps`。`summary` 的 schema 允许空字符串。审核员看到完整步骤，却没有被明确告知管理员只会看摘要，也没有最终审批展示正文的完整性检查。

**验证：**真实 schema 接受摘要“更新一个配置项”、实际步骤为覆盖 `server.properties` 加 `restart` 的提案；真实 `plan_text` 只输出该摘要。把摘要换成空字符串仍通过 schema。

**影响：**审核认为步骤符合任务，不代表管理员明确知晓批准包含重启、整份覆盖、移除旧组件或恢复范围。群消息不截断已经实现，但源展示内容本身缺项时，完整发送也不能补齐信息。

**最小整改：**在现有一次批准消息里，从受审步骤补关键动作、路径、启停和备份信息；把最终可见批准材料纳入审核一致性要求。继续保留摘要，不增加第二次批准。

**验收：**含重启、恢复或删除旧文件的方案，即使模型摘要含糊，管理员仍能看到关键实际动作；空白摘要不能产生空白方案说明。

### AR06：审核期间的新反馈没有阻止旧诊断

**位置：**`mcai/astrbot_agent.py:429-435、504-520、565-572、657-671`；恢复路径 `:737-788`。

审核完成后，只有 `mc_propose` 复查 pending。`mc_exec` 和 `mc_console_send` 仍继续提交；缓存审核失效条件也没有反馈版本。

**真实 runner／HTTPS 复现：**挂起审核，管理员通过任务补充明确要求“先不要执行上一条诊断，等我确认目标”，随后放行原审核。两个入口仍执行原调用：脚本完成并产生原标记；控制台发送 `list` 并出现对应新输出。两个“B 不应收到旧诊断”断言均失败。

**影响：**材料采集时是旧状态，审核返回时管理员意图已经改变，但旧诊断仍提交。已保存 allow 后中断再恢复，也存在同类源码路径。这里没有把正式 `/mcaipause` 或 `/mcaistop` 判成同一缺陷：它们另有 worker 取消和客户端停止检查。

**最小整改：**审核完成、尚未提交远程操作时统一核对真实反馈版本；出现新反馈就交回主模型重新判断。已提交操作继续遵循原编号结算，不能借重新审核重放。

**验收：**两个入口覆盖审核期间补充和 allow 落盘后续接；新增反馈能阻止尚未提交的旧调用，已提交调用不会被重复执行。

### AR07：系统恢复提示误使原提案失效

**位置：**`mcai/tasks.py:153-168`；`mcai/astrbot_agent.py:438-520、737-788`。插件重载的 `mcai/tasks.py:80-88` 也会追加类似系统提示。

**真实 runner／HTTPS 复现：**原 `mc_propose` 审核返回非法 JSON，任务暂停并保留 open step；管理员没有补充新意见，只执行 `/mcairesume`。第二次审核已经 allow，但 `resume()` 自动加入的 system pending 被 `if job['pending']` 当成新反馈，原提案报 `precondition_failed / 收到新反馈`，`job.plan` 仍是 `None`。

**影响：**原调用不能正常恢复，需要主模型再次提案和审核，增加无效成本；如果模型没有重提，会停在没有可批准方案的状态。AR06 是该拦截过少，这一项是用 pending 非空判定导致拦截过多。

**最小整改：**区分真实用户反馈与系统恢复提示，使用审核时的反馈版本判断原意是否变化；没有新信息时恢复原调用。

**验收：**审核故障后无新反馈续接，应恢复原提案进入待批准；确有新用户反馈时，旧提案仍应停止提交。现有故障恢复测试只覆盖了 `mc_exec`，见 `tests/test_review_resume.py:155-194`。

### AR08：只读数据参数被误认成待执行脚本

**位置：**`mcai/review.py:35-52`。

真实函数验证以下命令都会在审核模型请求之前报缺少脚本材料：

```powershell
Get-ChildItem -Filter '*.ps1'
Get-ChildItem *.bat
Write-Output 'notes.py'
```

这些命令列举或输出数据，没有执行外部脚本。补报 `script_files: ['*.ps1']` 也不能解决通配符问题，因为材料读取会把它当成实际文件。当前针对 `rg --glob/-g` 的排除只解决了一个特殊情况，未解决一般的数据参数误判。

**影响：**增加无必要材料要求并阻断正常诊断。`mc_exec` 本身仍应独立审核，问题在前置机械判定。

**最小整改：**将必须申报的机械检查收敛到明确脚本执行位置，完整原命令仍交独立审核；避免不断为普通工具名堆特例。

**验收：**上述查询可以到达审核，真实的明确脚本执行仍要求正文，同一条命令同时出现过滤参数和实际脚本时不能漏掉后者。

### AR09：无需启动的提案仍强制依赖启动脚本

**位置：**`mcai/astrbot_agent.py:458、498-501`；`mcai/operation_context.py:249-265、516-518、772`。

任何 `mc_propose` 都设置 `include_launcher=True`，读取并记录 `start.bat`；执行时复核全部脚本。因此纯在线公告、无备份的在线白名单命令、纯停服等无需启动的方案，也会受到启动脚本读取、解码和变更的影响。

**影响：**无关启动文件缺失、不能解码或审核后被修改，会阻断原本无需运行它的动作。启动配置哈希也对全部提案生效，可能让不相关的 Java 或启动设置调整使纯在线方案失效。这是多加了无关审核材料和执行依赖，不代表这些生产操作应该整体免审。

**最小整改：**按实际有效动作决定是否收集、绑定启动材料；先解决 AR02 的实际动作展开，再据此裁剪依赖，避免误删真实隐式启动所需的检查。

**验收：**纯在线无备份命令不依赖启动 BAT，显式或保留的自动启动仍读取和复核其材料。

## 已正确实现的保护

- 三个审核入口传递原始内联内容和实际步骤；已声明外部脚本由 B 读取实际正文，而非接受主模型转述。
- 已识别的顶层字面量脚本缺失、文件读取／解码失败、明确上下文超限不会静默裁剪后放行。外部脚本执行前校验 SHA-256。
- 审核是独立请求、无执行工具；严格核对 allow／deny JSON、字段集合、重复键及拒绝理由。失败不等于 allow。
- 反馈保留插件外层 `is_admin`，内置来源边界与运行时规则进入审核。脚本、日志和消息正文不应改变身份。
- 待执行提案再次检查参数、规则、协议和目标；多轮方案保存批准快照、原范围及身份，不由后续摘要改写。
- 执行编号先持久化，断线沿原编号恢复；续批入队有原批次结算保护。确定失败会终止活动多轮资格，新修复仍需重新提案与批准。
- 文件修改、安装和恢复走停服备份，并在对应步骤再次确认停服；失败保留部分效果与现场。
- 审核回复本地记录失败会停止执行，不因本地记录错误重复请求已成功的模型。审核申报和审核对话不进入主模型后续历史。
