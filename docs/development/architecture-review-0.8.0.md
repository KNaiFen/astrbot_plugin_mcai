## 结论与阅读顺序

现有 A 原生 runner → HTTPS operation → B 持久化 → 辅助工作进程／独立托管窗口的总体分工可以继续使用。原编号去重、先备份再写入、失败留现场、Markdown 经验库和共享 Job Object 都有明确用途。优先工作应放在**身份与状态交接的一致性**，其次是**历史数据增长和逐条处理开销**。

## 审查方法与边界

阅读了 README、使用／设计／开发索引，以及 Agent、状态恢复、终端资源、配置、存档联网、Probe、运行维护、测试、构建和来源说明。核对了 A 的任务和 runner、B 的操作分派、Store／Jobs、IPC、终端、配置、查询、下载、存档后端、Probe Java 采集逻辑及相关测试。仓库没有 `.codegraph/`，使用 FastCtx 按专题读取；未扫描上游或运行数据全文。

成功标准是：结论能回到当前设计约束和代码；行为缺陷有触发条件与实际结果；风险与实测分开；每项有最小改进和验收条件；文档可从索引找到、链接有效、能进入发行包；本地提交独立保存。

本轮实验均使用临时目录、隔离 HTTPS、受控 BAT／ConPTY、辅助工作进程或进程／网络替身。未操作生产实例、真实 QQ、外部模型或真实凭据。本轮未运行全量回归，也未重做四目标 Probe 服内验收；现有记录为 322 项完整回归及新增后 28 项相关复测，共 326 项已定义场景。本轮数字仅描述下方实验，不替代 [0.8.0 原验证记录](testing.md)。未进行网络安全或漏洞挖掘。

## R01：备份身份没有绑定规范目录

- **依据与位置**：设计要求规范目录作为身份。`mcai/host.py:490`、`:516` 的备份身份字段只有 `instance` 配置名，恢复也只比较这个字段；清单内的 plan 可能包含原 `expected_directory`，但恢复检查没有使用它。当前操作的 `expected_directory` 仅核对当前配置，不能核对备份来源。
- **触发与实测**：在旧目录用配置名 `same` 修改 `config.txt` 形成备份；把 `same` 改指向另一个目录，再恢复旧备份。新目录的原文 `new server original` 被替换为 `old server original`，流程返回成功。实验使用已停服终端替身，执行实际备份／恢复文件代码。
- **影响**：配置名复用后，批准恢复时缺少稳定的来源身份检查；反过来，同目录改配置名也会使原备份被当成其他实例。
- **最小改进**：新备份清单保存源规范目录，审核材料、恢复前检查和修复记录统一使用该身份。缺少来源身份的备份明确返回需人工核对，避免猜测关联。
- **验收**：同名不同目录拒绝恢复且新目录字节不变；同目录配置名变化时身份仍可解释；原有新增文件撤销、MCC 和失败留现场测试继续通过。

## R02：正常退出 B 的顺序破坏正在执行的修复

- **位置**：`mcai/host.py:1047` 的 `on_shutdown` 先关闭所有托管连接，`:774` 的清理随后等待 `host.workers`。修复步骤仍需通过 `mcai/execution.py:116` 查询终端状态或启停服务端。
- **触发与实测**：真实 HTTPS 下提交两步修复，第一步脚本写入中间值并等待，第二步写最终值；第一步期间调用 `AppRunner.cleanup()`。结果为 `failed`，错误为“托管窗口未连接或目标不明确”，只完成 1 步，文件停在 `middle`；托管窗口仍存活。
- **影响**：运行维护中“正常退出等待当前修复”的描述无法兑现；末尾自动重新启动同样依赖尚未断开的连接。
- **最小改进**：先停止接收新工作、完成已接受修复及所需终端 RPC，再断开托管窗口和释放辅助 Job／数据库。沿用当前修复步骤与 operation，不增加重放。
- **验收**：真实 B 正常退出覆盖备份中、脚本中、步骤交界和自动启动前四个时点；操作结果与磁盘状态一致，窗口和 MC 生命周期符合既定规则，退出有明确可观察的等待状态。

## R03：窗口已保存控制结果，B 没有把结果核对回来

- **位置**：`mcai/remote_terminal.py:122` 在断线时使待决 future 失败；`mcai/host.py:116` 将 operation 保存为最终 `failed`。`mcai/terminal.py:89` 已能按控制编号返回本地持久结果，但重连流程只发状态，没有由 B 核对未决控制的步骤。
- **触发与实测**：通过 B 提交 `stop`，窗口接受后断开 WebSocket。窗口完成正常停服并保存 `control.state=completed`、`running=false`，同 session 重连成功；GET 原 operation 仍为 `failed`，错误仅为连接中断。
- **影响**：连接故障被当作确定执行失败；AI 可能基于错误的失败判断继续提案。当前“直接调用 Terminal.dispatch 后断线”的测试只证明窗口继续工作。
- **最小改进**：B 区分确定失败与控制结果待核对，利用现有 `terminal_binding`、session 和原控制编号查询窗口持久结果。相同 session 核对结果，session 变化保留不确定状态。文件步骤不会因为此核对重新执行。
- **验收**：控制发送前、接受后、完成后丢失响应分别测试；同 session 取得原结果；新 session 不重放；A 沿原 operation 查询取得一致事实。多步文件修复中断后保留已完成位置。

## R04：配置忙状态以网络在线代替窗口生命周期

- **位置**：`mcai/host.py:174` 的 `instance_busy` 只检查 `window_online` 和 B 的活动操作／后台记录；`:181` 据此替换或移除配置。`terminal.py:63` 的终端配置是创建时快照；握手携带目录和状态，缺少配置身份核对。
- **触发与实测**：真实 ConPTY 窗口断开连接且没有活动操作时，desired 的 `stop_command=quit` 被立即应用；同 session 重连后，`configuration_pending=false`，B 使用 quit，存活窗口仍保留 stop。B 重启期间修改实例文件也存在相同配置来源分裂。
- **影响**：违反“窗口关闭且操作结束后切换配置”。改目录／删除更严重：旧窗口继续运行，却可能无法关联原配置，B 的审核环境与窗口实际执行环境不一致。
- **最小改进**：持久化窗口／session 对应的实际启动配置身份，断线保持未知或占用。重连核对同一快照；确认窗口结束后再应用 desired。继续使用当前 desired／active 机制。
- **验收**：窗口运行时断线、B 重启、同目录改停服参数、换目录和删除配置均覆盖；离线期间保持待生效，重连可说明实际配置；真正关闭窗口后才能应用。

## R05：真实扫描的取消不能打断输出等待

- **位置**：`mcai/world_tools.py:204` 仅在区域之间检查停止标记，`:221` 的 `process.stdout.readline()`、`:288` 的进程退出等待没有取消分支；`mcai/execution.py:189` 只对 `exec` 发强制取消消息。Java PID 位于 worker 的 `jobs.processes`，B 的该字典没有这个进程对象。`Jobs.cancel` 会等待 worker 结束。
- **触发与实测**：用接受启动后 30 秒不输出的受控子进程替代 Java，进入一次区域读取后置停止标记；0.5 秒后 scan 仍在等待。结束实验子进程后才返回“存档辅助程序提前退出”。这里复现的是阻塞等待机制，未声称真实 MCA Selector 必然卡住。
- **影响**：取消、停止任务、修复前清理和 B 正常退出可能被同一后台工作拖住；此前修复的排队锁取消没有覆盖这个阶段。
- **最小改进**：让正在等待区域输出的路径同时等待取消，取消后结束该扫描所属的 Java／worker 树并保存已确认进度；把等待收尾也纳入同一生命周期。文件修复仍在当前安全步骤结束后停止。
- **验收**：实际辅助进程分别阻塞在区域输出、stdin drain 和退出阶段；限定取消完成时间，其他实例及托管服继续运行，修复前清理可以完成，不重跑扫描。

## R06：Probe 取消结果与 worker 停止对象不兼容

- **位置**：`mcai/probe.py:114` 对 MOD 返回的 `status=cancelled` 调用 `jobs.stops[key].set()`；`mcai/worker.py:197` 的 `Stop` 只实现 `is_set()`。
- **触发与实测**：提前写入身份匹配的 Probe cancelled 结果，通过真实 `Host.perform → Execution → worker` 导入。后台任务变成 `failed`，错误为 `AttributeError: 'Stop' object has no attribute 'set'`。
- **影响**：MOD 自身取消、停服时返回取消或已有取消结果的导入被错误记为失败；测试侧 asyncio.Event 掩盖了契约不一致。
- **最小改进**：明确 worker 向 B 回报取消状态的方式，沿现有 RPC／Jobs 更新，不让代理伪装成完整 asyncio.Event。
- **验收**：缓存取消结果、运行中取消、服务端停止取消三条分支均经过真实 worker；任务为 cancelled，保留结果及 confirmed 信息。

## R07：远程取消失败跳过本地 finally 的清理

- **位置**：`mcai/tasks.py:611` 在 finally 内先 await `cancel_task`，成功后才保存状态并从 `self.workers` 移除任务。
- **触发与实测**：已停止任务的取消接口返回“实例不存在”。协程结束并抛出 RemoteError，`worker.done=true`，但 `worker_still_registered=true`、`cancel_pending=true`。
- **影响**：`wake` 无法重新创建 worker；设置页以 workers 是否为空判断忙状态，会持续拒绝保存。实例已删除等永久错误需要明确处理，而不能留下看似运行中的任务。
- **最小改进**：本地状态保存和 worker 移除放在无条件收尾；取消失败持久化错误及待处理事实。目录／实例身份核对后判断是否仍有远程工作需要清理，保留必要重试入口。
- **验收**：取消返回永久错误和临时断线分别验证；本地无已结束 worker 残留，错误可查，重载能按原事实继续清理，设置页忙状态准确。

## R08：分页发生在 IPC 之后，大结果提前失败

- **位置**：`mcai/host.py:403` 一次读完整 `script.log`；worker 最终结果受 `mcai/worker.py:22` 的 8 MiB frame 限制；`:82` 的 `Host.execute` 取得结果后才调用 `Jobs.result` 做大结果引用。NBT 和区域直接查询也经过这个顺序。
- **触发与实测**：临时备份放入 9 MiB `script.log`，经真实 worker 请求 `repair_log`，返回“辅助结果超过通信上限，请使用更小查询或分页”。该接口本身没有 offset 参数。
- **影响**：需要排查失败时反而读不到完整日志；共享内存额度不能解决通信上限。一次性 read_bytes 也会制造多份内存副本。
- **最小改进**：在结果产生端先保存大字段并返回现有 artifact 引用；修复日志按偏移读取，NBT 大字段同样走引用。IPC、B、A 和模型上下文使用一致的结果预算。
- **验收**：大于 8 MiB 的修复日志及单个 NBT 字段可续读至末尾；中文／emoji 不损坏；错误仍保留定位信息；整段结果不需要先经过一帧。

## R09：方案自己的写入使后续步骤必然失败

- **位置**：`mcai/astrbot_agent.py:297` 对所有提案读取启动器并记录哈希；`mcai/host.py:585` 在每个步骤前复核整组原脚本哈希。
- **触发与实测**：方案第一步 write_text 更新 `start.bat`，第二步更新普通配置。第一步成功，第二步因“审核后脚本已变化”拒绝，普通配置保持旧值；备份和第一步修改留下。
- **影响**：更新启动器／受审外部脚本的合法多步方案不能完整执行。错误出现前已经修改生产文件。
- **最小改进**：先定义方案允许的脚本变化语义。最小可行处理是提案阶段明确拒绝当前无法可靠执行的步骤组合，并说明拆分要求；若支持同一方案修改后继续执行，则审核内容与逐步期望状态必须一致。不能简单取消整组哈希检查。
- **验收**：同一方案修改 start.bat、修改外部脚本、外部人工变化分别覆盖；不支持的组合在停服与写入前拒绝，支持的组合按已审核内容执行完成。

## R10：已保存配置和运行配置的界面来源混淆

- **位置**：`mcai/host.py:821` GET 返回内存中的 PowerShell、Java 和额度；PUT `:859` 将新值写入 host.json，但这些字段重启前保持旧运行值。`views/settings/app.js:59` 用 GET 值回填，`:78` 再整组保存。
- **触发与实测**：PUT 内存额度 4096，返回 `restart_required=true`，磁盘为 4096；随即 GET 返回 8192。刷新设置页再保存其他主机字段，会携带界面上的旧额度。
- **影响**：用户看不到已保存待重启值，并可能无意撤销它。PowerShell／Java 同样有这类状态来源问题。
- **最小改进**：API 明确返回 saved／effective 与待重启状态，编辑字段使用 saved，运行状态展示 effective；保存后刷新可保持待生效值。
- **验收**：修改额度后刷新、只改 Java 再保存、B 重启后读取这三个流程；磁盘、编辑框、运行值和待重启提示一致。

## R11：拒绝更换目标前已经产生副作用

- **位置**：`mcai/tasks.py:265` 先取消原目标任务、清空 background／plan；`:271` 才检查新目标是否已被其他任务占用。
- **触发与实测**：原任务持有旧目标、方案和后台编号，尝试切到已暂停任务占用的新目录。接口拒绝切换，原 instance 保持不变，但 plan 已为 null、background 已为空，并已调用取消。
- **影响**：一次失败的选择破坏原任务的排查进度，错误提示无法解释这项额外变化。
- **最小改进**：先完成新目标可用性与当前任务可切换性的检查；只有切换能提交时再清理原目标并保存明确的切换状态。涉及 await 的步骤保留现有串行任务模型，核对跨任务选择是否需要同一把短锁。
- **验收**：目标不存在、待移除、已占用三种拒绝不改变旧方案和工作；成功切换仍按原编号取消所属工作，两个任务并发绑定同目录只成功一个。

## R12：常驻路径反复反序列化全部历史

- **位置**：`mcai/storage.py:38` 的 all 全量读 JSON；`Tasks.__init__:20` 加载全部任务含对话；`Tasks.deliver:155` 每秒读全部 outbox 后过滤 sent；`Host.instance_busy:174` 在每个实例的配置轮询中读全部 operation／background_job。
- **本轮测量**：临时 SQLite 写入 20,000 条已发送 outbox，每条正文 1,000 个 ASCII 字符；5 次热读 all 的中位数为 **94.88 ms**，每次仍反序列化 20,000 条。只是本机合成数据，不是生产 CPU 占用结论。
- **影响**：历史越长，空闲轮询也越慢；同步数据库／JSON 工作发生在事件循环中。辅助内存额度不覆盖 B 和 A 自身的这些分配。
- **最小改进**：先给待发送项和活动记录提供 SQL 条件查询及必要索引，限制批量；历史任务按需读取。沿用 SQLite，不需要更换数据库或引入缓存服务。
- **验收**：10 万已完成记录下，空闲轮询读取量取决于活动数；测事件循环延迟、查询耗时和 RSS；待发送消息与任务恢复顺序保持正确。

## R13：每条日志结果跨进程多次同步确认

- **位置**：`mcai/jobs.py:266` 每条 collect 调用 stopped、emit 和 update；worker 的 store.get/event/save 分别经过 `Channel.call`；`Store.event/save` 各提交事务。下载每 256 KiB 也保存一次进度（`downloads.py:261`）。
- **本轮测量**：1,000 条 `AUDIT line`，零前后文、单个本地日志，通过真实辅助 worker 返回 1,000 条结果，耗时 **2,964 ms**，状态 completed。包括首次 worker／模块启动和持久化开销，没有做冷热分离，不能把全部耗时归因到 IPC。
- **影响**：高命中日志或大量区域对象的吞吐受 RPC、JSON 和小事务开销放大；资源额度提供上限，仍会消耗不必要的运行时间。
- **最小改进**：结果按条数／字符预算组成小批次，B 单事务写入并确认；进度按有意义的增量更新。保留操作开始、文件步骤开始／完成等必须立即持久化的边界。
- **验收**：同一环境比较 1 千／1 万条，分开统计冷启动、记录吞吐、RPC 次数和数据库提交次数；丢连接后仅丢失未确认批次，分页序号和取消仍正确。

## R14：主任务上下文和总结输入无明确预算

- **位置**：`mcai/astrbot_agent.py:587`、`:611` 每步序列化并 deepcopy 完整 messages，`:648` 记录完整历史；`:659` 总结再次复制完整 messages、feedback 和 repairs。`Tasks.save` 把整个任务作为 JSON 重写。审核有 token 容量检查，主任务路径没有对应预算和持久压缩检查点。
- **影响**：长任务本地复制、SQLite 写入、审计文本和模型输入一起增长；达到提供商容量后可能只得到永久错误并暂停，续接仍携带相同历史。具体可承受轮数取决于模型和结果大小，本轮未测阈值。
- **最小改进**：先记录每步输入预算、任务 JSON 大小和错误原因；接近容量时形成持久的事实摘要与历史读取引用，保留目标、反馈、原操作编号、未结算工具步骤及修复事实。压缩边界只处理已结算内容。
- **验收**：构造数百轮工具结果，在模型预算内续接与验收总结；恢复时未结算 operation 不丢失、不再生成新编号；压缩后能追溯原始证据。

## R15：世界发现与区域过滤的工作量过大

- **位置**：`mcai/host.py:396` 每次 mc_status 执行 discover_worlds；`mcai/queries.py:50` 先 sorted 整个 glob，`:196` 两次递归枚举所有区域文件。`WorldTools.scan:156` 同步发现／收集，`:209` 复制区域与关联 MCC 后，`:240` 才按对象条件过滤。`snapshot:66` 对每个区域重扫同目录全部 MCC。
- **影响**：状态查询成本随全目录文件数增长；精确区块范围也可能复制并解码整世界；同目录大量 MCC 会叠加重复枚举。同步准备阶段还推迟 worker 处理协作取消。
- **最小改进**：先按区域文件坐标排除与 bounds 不相交的区域；一次扫描内复用文件／MCC 清单；世界发现按目录结构做有界结果，并保留明确刷新。过滤优化仍要正确处理不同数据集、负坐标及旧 MCR。
- **验收**：大目录、备份目录共存、负坐标边界和大量外部 MCC 场景下统计枚举／复制／解析数量及取消延迟；局部查询只处理相交区域；结果与原语义一致。当前没有大存档基准结论。

## R16：Probe 的局部范围和主线程 I/O 预算需收紧

- **位置**：`Probe.java:649` 迭代所有实体和 chunk holder 后才判断范围，`:663` 遍历每个 chunk 的全部方块实体；类别过滤在 `:684` 才发生。`:251` 取消通过 Files.exists 检查，由 tickStart／tickEnd 及各 Scan 直接在服务端线程调用。
- **影响**：玩家附近／单类型普查仍可能花费与全服加载量相关的迭代；扫描分批限制了单 tick 工作，却不能保证在 B 的 15 秒等待内覆盖完。约 1 ms 的普查预算也不能给一次阻塞文件 I/O 提供硬上限。本轮没有观测到真实服卡顿，不据此否定原有小负载开销记录。
- **最小改进**：在访问方块实体集合前先过滤 chunk／维度／类别；沿现有异步 I/O 线程获取取消事实，再由主线程读轻量状态。世界对象仍只在服务端线程读取，保持 getChunkNow 和不加载区块的约束。
- **验收**：十万级已加载对象下比较 loaded、player、精确 chunk 范围，记录 visited、完整率、耗时、tick 分位数和取消延迟；另测慢磁盘；确认访问未加载目标不会加载区块。

## R17：跨进程复用依赖半初始化对象

- **位置**：`mcai/worker.py:185` 用 `Host.__new__` 手动填 config／store／consoles／world／downloads；`:194` 用 `Jobs.__new__` 手动填内部字典。Host 同时承担配置、HTTP、修复、查询分派和生命周期，`apply_plan` 为 347 行；Agent.run 包含恢复、审核、工具路由和 runner 驱动。
- **问题性质**：文件长度只是定位线索，真正的问题是正常构造保证不再适用于 worker：某方法新增一个属性或 Stop 方法，另一执行环境不会自动获得它。R06 是已复现的具体后果。
- **最小改进**：先把 worker 实际需要的 store／console／停止与进度契约列清，使用正常构造或显式执行上下文，逐步消除 __new__ 拼装。提取仅限已经被主进程和 worker 共用的执行逻辑；HTTP 和 desired 配置继续留在 B。
- **验收**：worker 无需模拟完整 Host 生命周期即可执行既有操作；两种执行环境共用同一契约验证，包含取消结果与大结果；代码减少隐式依赖，没有再复制一套修复实现。
