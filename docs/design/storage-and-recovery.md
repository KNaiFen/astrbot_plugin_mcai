## 目标与任务状态

A的任务保存群、名称、发起管理员、问题、反馈、对话、方案、目标目录、操作和后台编号。任务名只在群内识别会话；规范化绝对目录用于目标身份，配置名用于B接口路由。

在 SQLite 的 `records` 表中，`task` 保存任务状态和元数据，`task_messages` 按同一任务编号保存完整对话数组。状态保存只写 `task`；对话变化时，两条记录在同一事务提交。上下文压缩仍可整份替换对话。加载和诊断导出会合并两条记录；若旧任务还将对话内嵌在 `task` 中，就使用内嵌对话，等这项任务下次保存时再拆分。升级无需批量迁移数据库。

待批准方案存入 `plan`。提案 ID 优先使用持久工具调用 ID；短码取该 ID 的 SHA-256 前六位大写十六进制，与同任务上一方案短码相同时取前八位。上一个提案的 ID 和短码随任务保存，重载或恢复同一提案时保留原短码。A 按当前待批准方案比对 `/mcaiapply 任务名 短码`，不区分大小写，批准人及时间随操作排队写入 `approval`，并记录 `plan_approved`。短码不参与审核参数哈希，也不发送给 B。

多轮方案使用任务JSON中的`approved_plan`保存批准快照、身份哈希、批准时间及执行状态，批准人和短码保存在快照之外。方案原文不随模型摘要或续批改变；当前批次仍为applied_plan/operation，结果沿用repairs并记录批准人。各批次独立持久化操作编号后才执行。续批排队后工具结果尚未保存时重载，先结算原批次，再恢复原工具结果，不重新排队。

普通补充只使未批准提案失效，已批准多轮方案保留；审核期间出现新反馈时本批不提交，模型读取补充后重新判断。提交替代方案、确定执行失败、停止或验收会结束原执行资格；规则、目标或批准快照变化使原批准失效。暂停保留批准记录。恢复先查询原operation，只有其结果已结算才决策下一批。mc_say等待补充时保持waiting；活动方案的单轮步数上限或普通final不会使连续调度提前结束。

待批提案失效时，pending和任务持久记录同时保存程序失效事件及原因；续接注入当前待批状态，模型须重新mc_propose。新的有效提案清除失效标记；尚未重提时最终群消息附程序核对的“当前没有可批准方案”，批准提示仍由有效方案通知生成。

任务的 `say_paused` 单独保存是否暂停普通成员say，新任务为false，已有任务缺少字段时按开启接收。开关重载后保留，独立于任务状态，管理员补充豁免。被拒消息不写pending、feedback或模型历史，不在恢复接收后补发。新反馈的 `is_admin` 与正文提示随记录持久保存；未记录身份的历史反馈保留原样，不能追认为管理员指令。

创建时目标可以为空，“待识别”由目标为空表示。AI查看已配置实例和历史，根据引用及自然语言选择；模糊时追问，不猜测。绑定时检查占用，每个实例一个活动任务，暂停继续持有占用。中止或验收后，只要`cancel_pending`尚未结算仍占用实例；取消失败与插件重载均保留此事实，后台清理成功后才允许新任务绑定。

以下组合以 `Tasks.save` 的保存点为准，包括中止、续接和异常路径中的中间快照。六种状态之外都会留一条违例审计。上次的 `applied_plan`、多轮方案记录、`repair_submitted` 和试服信息都可能作为历史保留；判断当前工作不能只看这些字段是否存在。验收已发布的任务时，`cleanup.pending` 可与取消标志一起出现在进入 `done` 之前。

| 状态 | 允许的当前工作和标志 | 保存点上的边界 |
|---|---|---|
| `running` | 目标识别和排查；可正在切换目标（`selection_cleanup`）、重试模型（`model_retry`）、生成待批 `plan` 或继续已批准多轮方案。批次结算后的首个快照可能仍有 `pause_after_operation`。 | 停止或验收请求可先置取消标志，尚未切到终态。 |
| `waiting` | 可有 `plan` 等待批准，也可无方案等反馈；`mc_say` 提问入箱后转入此状态；活动多轮方案可通过 `mc_say` 等必要补充或试玩反馈，或在一次空转提醒后等待管理员 `/mcaisay`。 | 有方案时必须有短码；取消请求和先前尝试留下的检查点不会因进入等待而统一清空。 |
| `applying` | 核对原编号或执行已批准批次；可有 `release_checkpoint`、`pause_after_operation`、`cancel_pending`。 | 必须有 `operation` 和 `applied_plan`，无待批 `plan`。多轮授权可以已失效或失败，此时仍须完成原批次的结算。 |
| `paused` | 可保留待批方案、未确认批次及提交标志、活动多轮授权、模型重试或目标切换检查点。 | 必须有 `pause_reason`；停止请求可以先保留暂停状态再进行取消。 |
| `done` | 验收结束；可能仍在取消后台工作，或正在清理试服、归档。归档模型可有 `model_retry`。 | 只有此状态可有 `archive_state`；取消结算后必须没有当前 `operation`。 |
| `stopped` | 已中止；可在 `cancel_pending` 下保留原批次编号并等待取消或恢复。此前的 `pause_reason`、模型重试和目标切换检查点可能保留。 | 不归档经验。取消结算后必须没有当前 `operation`。 |

| 标志 | 写入、清除与检查 |
|---|---|
| `plan` | `Tasks.propose` 写入，短码为 6 或 8 位大写十六进制。补充反馈、纠正目标、`queue_apply`、`stop` 或工作循环清空。检查：有方案必须有合法短码，且不与 `applying` 同时存在。 |
| `operation`、`applied_plan` | `queue_apply` 同时写入，与 `applying` 一起保存；`resume` 沿用原编号。批次正常结算、`AstrBotAgent.prepare_apply` 预检拒绝或任务取消结算时清空当前 `operation`；`applied_plan` 保留到下一批覆盖。 |
| `approved_plan.status` | `approve` 将多轮方案置为 `active`。`end_plan` 改为 `invalidated`、`replaced`、`completed`、`stopped` 或 `failed`，不删记录。检查只约束上述值；`require_plan` 在使用时核对快照目标和摘要。 |
| `repair_submitted` | 创建时为假；`Tasks.run` 在准备通过、调用 B 前置真。置真后保留并阻止改绑，不能单凭此字段认定 B 已接收，也不能反推记录一定有目录。 |
| `trial`、`trial_required`、`trial_published`、`trial_release_waived` | `AstrBotAgent` 的 `mc_say(test_operation_id)` 写入或更新试玩邀请；试服安装工作区制品后 `Tasks.run` 置 `trial_required`，正式发布成功后保存 `trial_published` 的批次编号；仅试服验证结案时 `finish_plan` 写入并持久化任务管理员的 `trial_release_waived`（`feedback_id`、`by`），正式发布入队时清除。它们不因清理而删除。检查：已发布必须有 `trial` 或 `trial_required`。 |
| `release_checkpoint` | 核对试玩反馈和批准后，发送前记录 `prepared`、完整请求及 B 操作库标识；取得 B 的原操作记录后才标 `accepted`。续接先查原编号；只有同库明确无记录、请求未变、批准及试玩反馈仍有效且未请求停止，才以原编号补交。未知时暂停并保留；旧记录若缺同库证据只查不补。必须有 `applied_plan.trial_release`。 |
| `cancel_pending`、`cancel_request` | `stop` 将 `stop_requested` 与 `cancel_pending` 同时置真；修复中提示当前步骤结束后停止。工作循环在调用 B 前保存 `cancel_request`；重载沿用原编号。B 结算本任务已提交的修复和后台工作后，A 保存终态、清空当前 `operation`、同步释放正式服占用，然后清理试服并通知。取消失败时保留占用并通知管理员。两者出现时都要求 `stop_requested`。 |
| `cleanup.pending` | 已正式发布的任务验收时记录发布编号；含试服的任务中止或仅试服结案时，在取消结算后记下原因 `aborted` 或 `release_waived`。B 先处理试服和暂存，再由 A 清理本地工作区和制品并结算。失败保留清理编号与错误，重载或下次绑定时重试。 |
| `pause_after_operation`、`pause_reason` | `pause_requested` 在批次执行期间设置前者；`run` 正常结算后取出并调用 `pause` 写入后者。预检拒绝或提前中止不走正常清理。`resume` 先写审计，成功后才取出原因；写入失败时任务保持暂停并报告错误。停止任务不会清除原因。 |
| `model_retry` | `agent_runtime.model_request` 写入重试与主备切换进度（含当前槽位、槽位失败计数与轮次），在成功、部分失败结算或缩小上下文并重发时清除；审核失效、新反馈或显式续接也可能清除。暂停、停止或归档重载时可保留。 |
| `archive_state` | 验收任务的取消结算后有目录且能总结时，`Tasks.run` 写 `pending`；`archive` 保存有效总结后改 `ready`，经验落盘后改 `completed`，失败保留原值。 |
| `selection_cleanup` | `select_instance` 在改绑前保存原目标的取消编号。原取消返回后，在锁内清除此检查点并重新核对目标；远端失败或中断时保留，直到按原请求结算。 |

`Tasks.save` 遇到违例记 `task_invariant_violation`，包含任务编号、违例列表以及调用栈摘要；生产仍继续原保存，审计 I/O 失败也不打断保存。测试在用例清理结束后扫描隔离的审计日志，发现该事件即失败。

以下两条暂不检查，靠生产审计观察：活动多轮方案的快照与当前目标一致（`require_plan` 在使用时核对并作废）；`repair_submitted` 必有 `directory`（按 B 已存在的操作编号恢复时不强制要求该字段）。

提交修复前可纠正目标，先取消原目标所属后台工作、清空旧方案，再加载目标经验。读取实例列表和取消旧后台工作不占用创建锁。取消期间原目录仍归原任务，结算后在锁内重新核对新目录占用，再绑定。已提交过修复的任务不跨实例切换。新操作带已选目录，由B执行前核对；目录变化时停止。断线后查询已提交请求，保持原编号和原参数。

## 操作与后台任务

设置页手动清理先生成选定任务和类别的路径、记录及摘要，再按同一摘要执行。A 根据持久化任务、待恢复工具／审核和当前多轮方案核对结算状态和引用；B 的 `POST /storage/cleanup` 沿用令牌与协议校验，接收 A 核对的结算状态，并独立检查未结算操作、后台任务、恢复材料及安装引用。归档先于删除，A 与 B 各自审计；跨主机没有共同事务，连接中断时通过审计核对结果，再重新预览。A 的 `settings_error` 记录清理任务编号、登录用户及预览或执行动作。B 文件删除后，同一数据库事务删除对应后台记录及 `job:<编号>` 事件，或删除对应暂存下载记录。后台清理留一条编号标记供查询报告「已清理」，保留原操作和审计。

手动清理从检查到删除与模型登记新工具引用共用一把独立锁，避免刚引用的数据被删除。建任务、绑定实例、启动任务或归档、保存设置使用原调度锁，不排在清理后面。单次清理的 B 请求各尝试一次，超时配置为 35 秒：预览最多约 35 秒，执行最多约 70 秒的网络等待（复核预览加执行）。模型登记引用还需等同一清理的本地打包及删除完成；这部分随数据大小和磁盘速度变化，没有固定时间上限。每次清理沿用开始时的 B 连接与 A 工作区路径。

批量预览按持久的结算时间选任务，再分别复用单任务保护和摘要校验；删除前复建批量摘要，每个任务仍单独核对快照，报告部分失败或跳过原因。自动保留期限默认关闭，首次检查在启动约一分钟后，此后每分钟检查本地日期，同一天只尝试一次；自动批次不接受备份类别。没有可靠结算时间的旧任务不会因创建得早而被自动或批量删掉。

两端各自在空闲时压缩 `state.sqlite3`，由现有数据库连接清空 WAL、执行 VACUUM，再清空 WAL，全程不让新的任务或操作进入本端执行。统计按 SQLite 空闲页数乘页大小报告可回收量。A 和 B 的审计、A 无任务留痕及 B 辅助进程日志在跨月首次写入或启动时归档；辅助进程错误输出由 B 主进程逐行写入。写入、轮转和按月删除共用日志锁，诊断导出在释放锁前取得归档及当前文件的读取句柄。归档只提供人工按月删除，详见[数据与备份](../usage/operations.md#数据与备份)。

A向B提交 `/operations/{id}`，B先持久化再执行。同编号同请求返回原记录，不同参数冲突；响应丢失后重连使用同编号，不生成第二个进程或修复。

B 主进程执行辅助进程回调时，除关闭时的协程取消外，异常均回复给辅助进程，原操作按失败结算并释放实例锁。备份空间预检或修复前置回调在停服或执行步骤前失败，标记 `execution_state=not_executed`；一旦发出试服停止请求，后续失败保留已知的试服状态，不标记为未执行。

提交记录落盘后若审计日志写入失败，B将原编号结算为`failed`并标记`execution_state=not_executed`，不创建执行worker。同编号查询、重提或取消均保留该失败，不重新执行。

工具调用按调用ID保存参数、审核状态、远程编号与原始result及模型可见model_result。远程执行前落盘，结果保存后才清理待处理步骤。恢复时先检查原操作与后台结果，再用普通调用相同的输出转换补回主对话，覆盖“B已完成、A尚未收到工具结果”的中断。导出保留两份结果，审核正文和申报材料不进入主对话。

诊断 ZIP 默认使用 `include_raw_api=false`（`manifest.detail=compact`）。它保留 API 请求的参数摘要、完成记录和用量，省略大段请求正文、工具定义与流式分片；`api_end` 保留 `chunk_count`，可测时附 `ttft_seconds`。需要原始报文和分片时设置 `include_raw_api=true`（`manifest.detail=full`）；该选项只改变导出内容。

B的日志检索、诊断进程、扫描和下载共用后台任务。启动最多等2秒，未完成返回任务编号；长工作不占用实例修复锁。查询、控制台和取消可以继续处理。默认结果按最多100条及字符预算分页，长字段提供引用与偏移续读，不能用整段硬截断代替分页。

A在后台等待期间仍接收带命令的反馈，下一模型步骤可以调整方向或取消工作。修复执行前先结束该排障任务的诊断和扫描等后台工作，保留其他任务的工作。

新工具结果进入主模型前按当前请求的可用输入额度分配整组展示预算；单项超额时，完整结果写入当前任务既有context证据与索引，模型只接收状态、原编号和`mc_context_history`续读入口。原始result与evidence_id不变，不为读结果重跑操作；原助手／工具调用配对保持。原文续读页长随同轮预算缩小，不改已保存的旧历史。

大结果在worker内先写artifact再返回引用，避免整段结果跨越8MiB帧。修复日志按字符偏移读取。日志结果按100条或24000字符形成确认批次；输出和进度同事务保存，断线仅可能丢失尚未确认批次。操作和文件步骤的开始／完成仍立即保存。

内存趋势样本保存为后台任务的 `memory-trend.json`。堆转储写入 B 的隔离任务产物目录；失败时保留已有文件并将后台状态标记为失败。`hprof-summary` 可流式读取 `.hprof.gz`，无需先在磁盘展开成 `.hprof`。

主任务以模型 `max_context_tokens` 的 85% 作为压缩水位（未设置时沿用 272000），并尊重预留输出后的输入上限；系统规则和实际工具定义均计入。在触发压缩前，有效历史前缀只追加，不原地裁剪旧工具返回，供服务商复用提示缓存。相同前缀以 API 输入／输出用量加新增消息估算；前缀、模型、规则或工具变化后重新估算。任务私有提供商禁用原生 runner 的自动截断。

主请求只发送一份稳定系统提示：Responses 放在 `instructions`，Chat 放在消息列表首项。实例、方案和工作流变化通过尾部程序消息传递，补充提醒紧随真实反馈。程序消息以 `developer` 落盘，Chat 发送视图投影为 `user`。Responses 默认用任务编号生成 `prompt_cache_key`，服务商明确拒绝时在本轮私有提供商移除它并重试。包含 `web_search_call` 的实际用量照常记账，容量估算继续使用上次匹配前缀的无搜索样本或校准估算。

计数复用AstrBot字符估算；既有102个真实主请求样本最大比例1.377，主请求基准取1.4；真实日志摘要294090／187935=1.565，摘要／审核／归档冷启动基准取1.6。校准按估算器版本／提供商／模型／参数／用途隔离，记录有效实际用量与原估算比例及5%余量。远程压缩检查点的已知 token 数直接计入，不乘字符估算系数；包含检查点的请求仍可用实测输入和输出校正匹配前缀，但不生成校准样本。工具结果展示先把可用输入额度换算回对应估算单位。摘要预留显式配置的输出额度；未配置时，私有摘要请求设置最多8192 tokens且不超过窗口十分之一的输出额度。未知模型和未覆盖文本仍是估算，超限继续缩批，原始证据与操作不重放。不引入本地分词库和词表。

按完整消息组划分历史，工具调用与全部返回同组。发送前补齐历史中缺失的工具返回：按原调用顺序补上标记为 `aborted`、执行状态为 `unknown` 的占位返回，移除孤立或重复的返回，并记录修复日志。已保存的待结算步骤仍优先按原编号恢复。压缩保留最新用户原文和最后一个已结算助手组，预算允许时额外保留最近管理员补充和最多 40000 tokens 的近期交互。紧急压缩先缩小额外保留范围。已入库的原始 `result` 和 `model_result` 不变，旧任务遗留的存根仍可续读原文。

达到硬水位、超出输入上限或 API 明确报上下文超限时，默认使用独立摘要请求。可读投影保留 Responses 消息阶段，排除推理载荷，并将大型工具输出先收成有界预览及证据引用。摘要流式接收，私有 SDK 客户端使用 300 秒网络操作超时。Responses 须为 `completed`，Chat 须以 `stop` 结束；完整非空且确实缩减历史的结果才替换活动历史。

Responses 启用远程压缩时，达到水位后优先压缩受保护尾部前的完整前缀（含已结算的早期用户轮次，管理员原话同步记入事实台账），流式触发模式沿用主请求的系统提示、思考参数、工具和任务缓存键；独立接口为兼容模式。原前缀和索引存入 SQLite，活动历史保留原生回放项和程序事实台账。密文按 API 返回用量估算回放大小。网络中断或服务商临时错误走持续重试；接口明确不可用、拒绝密文、结果无效或压缩请求超限时，仅当前任务切回传统压缩。兼容的检查点可和新增历史的五节摘要并存；无法缩减或密文被拒时递归恢复原文。提供商、端点、模型不匹配时读回原文并去掉加密推理字段和原生推理项；验收归档的可读投影同样排除推理载荷。

最新用户消息只在主历史完整保留，不重复加入旧历史摘要请求。尚有真实旧历史时，本批至少包含一个真实已结算组，不只重压刚生成的检查点；下一完整组确实装不下时准确报告该组容量，原文不变。

过大历史按完整组分批处理，API 报摘要超限时缩半后重试。首次写五节交接摘要；后续只传上次摘要正文和新增旧历史，事实台账由程序直接合并。每批先保存 SQLite 原文和索引，再保存检查点。除任务描述、目录和操作／后台编号外，检查点保留最多 4000 字符的近期管理员原话及最近 32 条证据引用；成员反馈和不可信附件不得写入管理员台账。原文由 `mc_context_history` 回读，后续失败保留已完成检查点和未处理历史。受保护内容、单组或无法缩减的摘要超限时明确暂停；未结算 `open_step` 仍按原编号恢复。验收整理只在独立工作副本使用这套机制。

历史本身仍无法容纳时，暂停提示给出当前窗口、所需输入、预留输出和建议容量，指向AstrBot模型的`max_context_tokens`配置及续接命令。管理员须先确认服务商支持更大窗口；不支持时保留旧任务证据，另建更小范围任务。仅重复续接不会改变已存在的超大受保护组。

## 模型失败、暂停与停止

进行中任务的排障、审核、上下文压缩与审核历史压缩，API 请求错误默认持续重试（400／404／422 等永久客户端错误在未配置备用时快速结束；远程压缩明确不可用、拒收密文或超限时直接切回传统压缩）；独立搜索 `mc_search`（`alpha/search`）端点绑定且不参与主备切换，沿用有限次数重试。未配置备用时，普通错误等待 2／5／10／20／30 秒随后固定 30 秒，401、认证或权限类 403、明确额度不足的 429 等待 300 秒，上游明确拦截特性的 403 快速结束。

排障与独立审核通过统一的 `ModelFailover` 各自维护独立的主／备提供商解析与冷却驻留窗口（进程内按 `(主 ID, 备 ID)` 隔离；未配置备用时完全沿用单 API 行为）。配置备用后：当前通道在普通可重试错误下连续失败 3 次（2／5 秒退避后立即切槽），或遇到 401、非特性拦截的 403、明确额度耗尽的 429、404 及模型不存在／密钥无效类配置错误时立即切到另一通道；内容过滤、输出截断、本地用量写入失败、一般 400／422 参数错误及审核 `ReviewProtocolError` 均不触发主备切换。备用请求成功不发群告警，记录 `active_provider_id`/`active_provider_slot` 与本地日志，并开启 `backup_cooldown_minutes` 冷却驻留（窗口内不再顺延）；驻留到期后先以单次探测尝试主 API，成功则清冷却切回主，临时失败则立即切回备用并续期冷却。主备通道均失败时发出一次合并群告警（同阶段 15 分钟限频），随后按轮间退避（主备均为配置／认证／额度问题等待 300 秒，429 按限流退避，其余按 10／20／30 秒）主备轮流重试。跨异构提供商（如 Responses ↔ Chat）切换时，备用通道的特性降级标记隔离保存在 `backup_provider_flags`，加密推理密文按 `reasoning_identity` 仅对不匹配提供商在发送视图跳过而不改动存储历史，不匹配的远程压缩检查点由 `fit_history` 自动还原原文。

`model_retry` 保存轮次、阶段、总尝试、当前通道与槽位失败状态、连续失败计数和起点、错误类别、下次重试时间及通知标记。插件重载沿原轮次继续；成功清除记录，上下文缩减或用户反馈改变输入时开始新轮次。认证、权限和额度错误在单 API 模式下首次出现提醒，普通错误在第三次失败提醒；配置备用后仅在主备均失败时提醒。使用持久化发件箱及轮次 ID 去重，正文只含阶段、错误类别及控制命令。配置自动暂停后，重试等待期间达到连续失败时限便暂停，续接保留该轮输入和编号，重置等待、连续失败计时并优先切回主 API；已有反馈仍优先。管理员手动暂停／停止取消当前模型协程及退避，已提交修复保持原安全步骤行为。审核协议非法输出（`ReviewProtocolError`）仍在当前审核模型最多 3 次、不切备；`/mcaiask`、验收归档与群图片识别共享主角色 `ModelFailover` 冷却并采用有界每通道重试（不触发任务暂停或群告警）。

模型用量在私有 API 追踪边界按请求结束记一次，流式采用最终返回的用量；正常响应、失败和取消无重复记账。每日总量按 A 的本地日期、提供商和模型汇总；同一 SQLite 事务还更新任务的用途明细或非任务日汇总。设置页汇总最近 30 天的日用量，任务明细单独读取。独立搜索和能力测试也通过该边界。缺少用量和缺少缓存命中各自计数。本地用量写入失败时保留追踪并停止该任务的模型重试，避免对同一请求再次计费。

进行中任务在模型请求前后检查已累计的输入＋输出。80% 提醒状态和续接份数随任务保存，每次批准续接增加一份基础额度。达到上限时暂停，不让新返回的工具请求产生操作；已有远端操作沿原编号结算。验收后的归档仍记入用量，保留原归档流程和有限重试。

主模型、独立审核和验收归档都在接纳结果前检查原始完成状态：Responses 须为 `completed`，函数调用项如带 `status` 也须为 `completed`；Chat 主请求允许 `stop`／`tool_calls`／`function_call`，摘要仅允许 `stop`。达到输出上限（`max_output_tokens`／`length`）或被内容过滤（`content_filter`）时，不在同一请求上反复重发，也不准备工具调用、形成审核决定或写入经验。明确拒答不能作为压缩或验收摘要。归档对这两类未完成输出及 403 等永久错误提前结束，其他临时错误沿既定退避处理。

审核响应通过协议校验后，本地审核记录在模型重试边界之外保存。记录失败会明确暂停且不执行操作；已成功的模型请求不因该本地错误重发，原始响应仍由API追踪保留。

复用AstrBot安装的官方OpenAI SDK，通过with_options(max_retries=0)建立任务私有客户端；资源方法、api_key和timeout均绑定该实例，搜索与进度包装在同一实例上组合，共享提供商配置保持原样，底层HTTP连接池由SDK复用。插件向提供商传递单次请求尝试设置，由任务层管理重试；不修改AstrBot源码和共享配置。

Chat／Responses主请求均优先流式接收，群进度开关只控制commentary转发；服务商明确返回400／422并说明不支持stream时，本轮使用非流式兼容路径。主模型、审核和验收请求沿用提供商超时，压缩单独使用300秒网络操作超时。流式留痕按Responses终结事件或Chat各choice的结束原因结算；Chat继续读取usage尾片段，每个请求只记录一次api_end。非流式响应也按status／finish_reason记录完成状态。

`mc_say` 提问或邀请试玩、普通 `final` 结束本轮、步数用尽、多轮方案续接停滞和空白创建进入 `waiting` 时，群消息会 @ 任务管理员（`job["admin"]`），说明自动排查已暂停或尚未开始，并提示通过 `/mcaisay` 补充或在适用时通过 `/mcaidone` 验收结案。`/mcaisay` 可直接启动下一轮。`mc_pause` 用于需管理员处理的 `paused` 状态，只通知一次，保留占用、上下文、反馈、审核与远程编号；此时 `/mcaisay` 只保存反馈并回复仍暂停，须用 `/mcairesume` 显式继续。

主模型生成或退避期间收到`/mcaisay`，先保存pending，再通知任务私有MainProvider取消尚未完成的主生成，将反馈加入原生runner消息并检查上下文预算，再重新请求；新补充不计为模型失败。历史压缩期间收到的say等待压缩完成，再与摘要和保留原文一起进入下一次主模型输入，发送前重新检查预算；阈值触发和接口超限后的补救压缩均按此规则处理。Chat与Responses均支持。正在结算的工具不被反馈重放；工具返回后读取新消息。审核期间到来的反馈不进入审核对话，且阻止旧提案成为可批准方案。未返回的内部思考从最近保存的消息和工具事实重新请求，不恢复模型内部状态。

停止会打断模型请求和退避等待，取消所属后台工作。已进入的文件修改步骤完成后停止后续步骤。修复错误与网络结果不确定要区分：不确定时查询原操作；确定失败后停止原方案，保存已完成步骤、失败步骤、备份和服务端状态。

确定失败会把修复记录、状态和控制台交给AI继续检查。新证据支持新方案时重新审核和批准；无方向则 `mc_pause`，不能无新证据重复相同失败方案。用户已停止后不再自动分析。

## 故障留证

Web 管理读取与 A 的通知游标分开。B 的事件历史按序号逆序分页，可按实例、事件类型或仅现有实例筛选，并单列活跃健康告警；A 的失联与恢复从本地分页读取。实例删除、换目录或停用对应检测时，B 按实例、规范目录及告警类型清理失效的活跃状态，不新建恢复事件。历史仍按留证库容量淘汰。附件只按事件 ID 和已登记的附件 ID 查询同一 SQLite 记录，预览沿用有界读取；下载传输原始 gzip。备份清单按持久操作定位，定时备份使用该次操作已保存的根目录。

B 按规范实例目录、托管会话、Java PID 和创建时间为本轮文件归属做记录。独立观察退出，确认无下一轮 Java 后直接流式复制为 gzip 并计算原文 SHA-256；同一文件只追加或边界不可确认时跳过。连续失败在 B 的 `incident-staging/` 暂存最近三轮，前两轮不写事件；超窗、恢复、断线或 B 重载时清理未成案副本。归档文件以 gzip 分块存入同一事件事务，随事件一起淘汰。读附件使用事件和附件编号，沿用正式实例目录校验。

B 可按实例开启只读观察。异常事件保存原因、进程状态、相关操作及故障当时冻结的控制台缓冲区。正文分块压缩，与事件头一并提交到 `data_dir/incidents.sqlite3`，按实际数据库页控制占用，按整起事件淘汰。升级导入旧事件时保留编号和通知序号；旧记录仍标记为尾部证据。故障前性能只在内存按 JVM 与 Probe 会话保留，事件只附出事会话的成功样本。A 只向明确配置的群路由通知已提交的事件；Agent 按已绑定实例和规范目录查询，原文不自动入群。配置见[故障留证与通知](../usage/configuration.md#故障留证与通知)。

主动告警与留证分别开启。B 每 5 秒观察正式实例：托管窗口以已记录的连接为入口，磁盘同时检查实例目录盘、B 数据盘，以及与 B 数据盘不同卷的当前定时备份目录，沿用实例的阈值。空间持续不足 15 秒发告警，实例目录盘或 B 数据盘不足时附带 B 数据占用；所有受监控盘均达到阈值再加 1 GiB 才报告恢复。性能只接受同一 JVM 与 Probe 会话的新鲜心跳，缺样本会清零持续计时，不发恢复。窗口、磁盘和性能各自计时。B 在 SQLite 同一事务存入告警状态和事件；重启后保留已发告警及一小时限频，未达到阈值的计时重新观察。告警和恢复共用原留证事件序号，带独立类型和查询编号，不替换故障留证的活动记录。

A 每轮只请求一次 `/incidents`，有超时。首个失败时间、已通知状态和恢复记录都保存在 A；每次告警或恢复与群发件箱在同一事务保存，按路由目标去重。B 事件按留证库标识、序号和末事件 ID 续读；A 在同一事务入箱并更新游标，离线平台由对应群的发件箱重试。换库或检测到序号回退时，从留存事件重读并按事件 ID 去重。若恢复的旧副本已写到原游标之后且该位置已裁剪，不能依赖序号识别回退。A 自己检测到的 B 失联记录不依赖 B，任务可从同一群用 `mc_query incidents show` 按编号查询。

## 定时维护

网页登记和编辑与 QQ 管理复用同一调度库和替换约束。网页编辑会生成新编号，并保留原计划的暂停状态。A 在提交网页启停前记录 B 库标识、规范目录和操作编号。响应丢失时先查询原库；B 若尚未受理，可按原编号阻止迟到的提交。已受理的请求保留原状态，不重新执行。群任务绑定与网页提交共享 A 的调度锁。

直接启停只有在原 B 操作库确认单一步骤的停止或重启仍在执行时，才可升级为强制操作。A 先请求取消原等待，最多等 10 秒；未结算时保留原编号。释放后重新读取实例、托管会话与进程身份，群确认单仍须匹配。若已经停稳，强停返回已停止，强制重启只提交启动。活动群任务、定时维护和包含文件变更的方案不允许被升级打断。

B 保存审核通过且由管理员批准的计划参数、规范目录、下次时段和上次结果。登记绑定审核凭据和操作编号，重发使用原编号；替换计划分配新编号。B 每轮按本地时间扫描，每天或指定星期的时段落下时，在同一 SQLite 事务中推进下次时段、分配本次操作编号并记下待执行操作。维护走现有实例锁；B 重启后只续接尚未开始的时段，已开始的以原编号结算，避免停启或复制重放。B 停机期间错过多次只处理最近一项：备份补跑，重启记录跳过。本地时间因夏令时跳过的时刻不落时段；重复的时刻执行一次。

调度数据库暂时不可用时，B 保留已记下的时段和操作编号，退避后从原状态继续；计划列表显示独立的调度降级状态。原窗口的保存恢复按实例等待，其他实例仍可调度。

实例修复或原托管窗口尚在重连时推迟维护；A 轮询事件时一起上报活动任务所在目录，并在绑定、切换目标、任务释放占用及提交直接启停前立即同步刷新该目录集合（轮询期间若占用变化则追加一次同步），只额外阻挡这些目录的重启。常规推迟从原执行时间起最多 30 分钟；停机补跑的备份从发现时起算。A 上报超过两分钟时视为未知，并把此状态写在重启结果中。暂停和删除可以结束尚未开始的时段，运行中的操作继续结算。运行结果和推迟事件共用留证事件流的序号，不占用原故障状态。通知由 A 按路由投递，普通成功默认不通知。

在线备份先核对容量并登记原窗口会话和 Java PID、创建时间，再发 `save-off`。从本轮 `save-all flush` 返回的控制台游标之后等待完整保存回执，再复制，收尾补发 `save-on`。控制台没有逐命令回执编号，在线备份期间应避免并行手动保存；需要明确一致性的操作使用停服备份。B 重启会先等原窗口重连，窗口或 JVM 已变更时只记审计。同一会话的补发复用原控制编号。停服备份复用停启服路径；重启复用停启与就绪检查，沿用 BAT 启动方式。定时备份与修复备份沿用同卷空间预约和同一清单格式，在线复制跳过世界的临时文件 `session.lock`。只按计划编号轮替该计划已完成的备份，有活动引用时暂缓删除。

## 两类重启

- A插件重载：恢复运行任务、原工具步骤和后台编号；已暂停任务保持暂停，待归档工作可继续。
- A冷启动在AstrBot启动完成钩子中恢复任务，避免先于模型提供商加载。运行中安装／热重载在提供商已存在时直接恢复；收到真实群命令也会启动尚未运行的任务服务，各入口只启动一次。
- B控制程序重启：未完成操作以原编号结算为 `failed`，其中 `pending` 标记 `execution_state=not_executed`，`running` 标记 `execution_state=unknown`。A 不重放修复；状态不确定时按失败结束原多轮方案的执行资格，模型先用 `mc_operation_read` 和现场核实实际效果。后台任务标记中断，保留输出并按进程身份清理诊断子进程。
- ConPTY由各自托管窗口持有，B重启后按目录与会话重连。窗口更换会话时旧控制操作不重放；状态未知时不认定已停服。

群通知使用持久发件箱。新消息入箱、手动重试或同目标前一条送达后立即唤醒发送循环，无需等待下一次轮询；同一 `origin`（平台会话与目标群）按 SQLite 入箱顺序处理未送达消息，其他目标并行发送。失败按 2／5／10／30／60 秒退避，之后每 60 秒继续尝试。队首在同一未确认分段连续失败 3 次后，在下一次重试时先试队首；若仍失败，再试发同一目标的下一条消息。探测成功则持久标记队首为单条故障，让它继续独立重试，其后的消息仍按顺序处理；探测失败则保持原队列。分段和无任务的故障通知遵守同一规则。

发件箱保留已确认分段数、分段尝试次数、总尝试次数、失败次数、首次失败时间、最近错误和下次发送时间。首次失败审计保存正文和调用栈，之后只在每第 10 次失败或错误内容变化时记录摘要；成功后另记总尝试次数和首次失败时间。重载从未确认部分续发并保留排序和退避。发送成功但回执丢失时仍可能重复通知，这不导致远程修复重复执行。

旧 `failed=true` 记录保留在设置页，暂停自动发送且不阻塞队列，手动重试后按原入箱位置排队。手动重试清除等待时间，丢弃则结算为已丢弃并审计登录用户与时间。已停止或找不到任务的未发送进度仍会丢弃。

## 经验文档

网页可按文档读取、搜索和编辑案例，新增人工案例或删除指定案例；也可创建实例文档、修改目录关联、解除关联及删除孤立文档，正文和索引可直接编辑 Markdown。网页编辑与经验归档共用 `tasks.knowledge.lock`。保存核对文档或索引版本，索引校验 JSON、规范目录与关联文件。通过校验后用临时文件原子替换，并记录网页修改；非法索引返回具体行号，文档仍有关联时不能删除。

任务和执行状态使用既有SQLite记录；经验知识本身只用Markdown：

```text
A插件数据目录/
  knowledge/
    index.md
    servers/<规范目录标识>.md
```

索引保存规范目录到文档的关联，可人工调整；不绑定公网IP或仅按配置名分文档。实际搬迁目录默认新实例，当前模型为一台B的多个实例。

`/mcaidone`验收后，主提供商以独立、无工具请求总结已返回对话、反馈和修复事实，排除审核申报与响应，未知原因写未知。先持久化总结，再串行原子追加文档和索引，按任务编号防止重复。已有内容和人工编辑保留。

归档复用排障模型的思考强度；完整存在于历史明文中的反馈不重复补入，压缩后缺失的反馈及修复记录仍补入。归档前按问题与管理员反馈提供最多三条相关、有效旧案例（排除本任务，合计不超过1200字符）；读取失败留审计并省略参考，不阻断总结，实际写盘仍严格校验索引。

新归档顶部用可直接编辑的中文列表声明元信息，正文典型案例建议500~1500字，所有子节使用三级标题，结论置顶：

```markdown
- 标题：概括对象与核心现象或操作的20~40字语义标题
- 类型：故障排查
- 状态：active
- 关键词：模组名、异常类、配置项
- 环境：MC版本 / 加载器 / Java版本，未知写未知
- 替代案例：无
### 结论与适用条件
首句给出核心结论及适用前提。
### 依据或故障原因
### 实际操作与验证结果
### 失败尝试与避坑
### 备份与恢复线索
### 来源与边界
```

类型可选故障排查、性能优化、日常运维、MOD与配置变更、存档维护。标题写入案例二级标题时保留任务名；普通文本归档保持旧标题及正文格式。摘要优先取“结论与适用条件”或“结论”首段；旧案例回退取跳过元信息和标题后的首行正文。

只有新结论明确修正或覆盖所提供旧案例时，才声明“替代案例”的旧编号。解析仅认同一文档中先于本案存在的编号，忽略自引用、未来编号与未知编号。被替代者或显式声明superseded者的有效状态为superseded；不回改旧正文。删除替代者后原案例自动恢复active，原本显式声明superseded的案例除外。

Markdown始终是经验的单一事实源。进程内按文件mtime_ns和size缓存解析与词频；人工修改或原子替换后自动失效。检索使用纯Python BM25、中英文标识符与中文二元片段、通用停用词过滤、标题/关键词3倍及结论2倍权重和轻度新近加成，无额外数据库或分词依赖。

`mc_history(mode="list")`默认列最新20条active案例，limit为1~50，offset按案例下标，status可选active/all/superseded，category按类型精确过滤；返回total、total_all、superseded_count、items及next_offset。`search`支持多词与all_servers，默认8条、上限20条，offset按命中案例下标；保留单份带case_id、目录、状态、命中词及行号片段的聚合text，按相关性排序。跨服检索不能同时传directory，缺失关联文档列warnings与warning_count（最多展开八个路径，其余汇总数量），其余损坏明确报错。两种模式单页均不超过12000字符，沿next_call续页。read/index仍按字符分页；按编号用mc_knowledge读详情。

绑定预览始终给出total_cases和active_cases；相关命中最多四条，superseded在有active命中时显著降权并显示替代编号。零命中则提示检索全部历史并列最近最多三条active案例，整个预览不超过1600字符。目录及搜索默认隐藏superseded，status=all可回查。

归档不阻塞任务结束、不持有实例占用。任务中止、仅试服结案或正式发布后验收，会沿持久化编号清理 A 工作区、制品暂存和 B 试服，保留正式备份和操作记录。未发布试服先正常停服，等待约 15 秒后取消停服等待并升级强停，再关窗并删除。自动清理失败时，可在「运行概览」手动删除并结算 A 的待处理清理；已结算任务的旧试服目录也可通过「数据占用」按预览清单清理。经验读取支持索引、关键词与分页；绑定时提供案例目录和相关片段。历史仅为线索，不能当作新修复的证据或授权。

归档重试成功并完成经验写入后清除当前archive_error；历史archive_failed审计记录保留。自动重试和插件重载续接使用相同结算路径。

已验收或停止的任务在取消、归档和试服清理均已结算、两个工作协程均退出后，从 A 的内存任务表和对话保存缓存移除。诊断导出和手动清理从 SQLite 读取历史任务；重载仍按原规则恢复尚未结算的任务。

归档压缩使用局部工作历史和独立 `archive_context_budget`。在归档摘要前，按工作历史中 Tier-1 的 `evicted` 存根，以工具调用编号从 SQLite 读取原记录；优先补回近期证据，每条最多 3000 字符，合计最多 24000 字符且不超过模型窗口的十分之一。归档模型没有工具，直接从副本读取这些按载荷优先并保留正文首尾的紧凑证据预览。主任务的 `messages`、`context_usage`、存根和原始工具记录都不改动。已准备输入按任务保存为 `archive_input`，绑定提供商／规则／原历史／反馈／修复事实；最终总结失败重试时复用同一准备结果，输入版本改变才重新准备。
